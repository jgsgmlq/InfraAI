# SDK 稳定性原则设计文档

**日期**: 2026-03-06
**状态**: 已批准
**作者**: AI + 用户协作

---

## 问题陈述

当前的 SDK 设计文档没有明确体现"SDK 是稳定工具库"的原则，导致 AI 可能会在用户进行项目开发时随意修改 SDK 代码。这违反了工具库的稳定性原则，可能导致：

1. SDK 代码被项目特定的需求污染
2. 框架的可移植性和可维护性下降
3. 用户难以区分"框架开发"和"项目开发"

---

## 核心架构理念

### 架构定位

`D:\infra_demo\` 是一个**可移植的 IDE 平台**，包含两层：

1. **框架层**（稳定，不随意修改）：
   - `sdks/` - SDK 工具包
   - `scripts/` - 框架工具
   - `.claude/` - Claude Code 配置
   - `docs/` - 规范文档
   - `CLAUDE.md` - 项目上下文

2. **项目层**（用户工作区）：
   - 用户在根目录下创建的项目子目录
   - 例如：`my-web-app/`、`data-analysis/`、`another-project/`

### 架构类比

- **SDK 框架** = npm 包库（提供可复用的工具）
- **用户项目** = 使用 npm 包的应用（调用工具，不修改工具源码）

---

## 工作模式定义

### 1. 项目开发模式（默认）

**定义**：
- AI 在 `D:\infra_demo\<project-name>\` 子目录中工作
- 调用 SDK 提供的 API、CLI 工具和 skills
- 不修改框架层文件
- 新功能先在项目中实现和验证

**典型场景**：
- 创建新的 Web 应用
- 实现业务功能
- 修复项目 bug
- 添加项目特定的功能

### 2. SDK 开发模式（受限触发）

**定义**：
- 只有在明确条件下才进入此模式
- 可以修改 `sdks/` 目录下的代码
- 可以创建或修改 SDK 工具和 skills
- 可以修改框架层文件

**触发条件**（满足任一即可）：
1. 当前工作目录是 `D:\infra_demo\`（平台根目录）且命令涉及修改框架层
2. 用户明确下达命令（"修改 SDK"、"扩展 SDK"、"创建 SDK 工具"等）
3. 用户的命令意图明确表示要修改框架层文件

---

## 模式识别机制

### 默认行为

AI 默认处于**项目开发模式**，除非明确触发 SDK 开发模式。

### 触发条件详解

#### 条件 1：工作目录判断
```bash
# 当前在根目录
pwd  # 输出: D:\infra_demo

# 且用户命令涉及框架层
"修改 sdks/infra-core/api/audit.py"
```

#### 条件 2：明确命令短语
- "修改 SDK"、"扩展 SDK"、"创建 SDK 工具"
- "更新 SDK"、"SDK 开发"、"编写 SDK"
- "修改框架工具"、"扩展框架"

#### 条件 3：命令意图分析
- 用户的命令明确提到要修改 `sdks/` 目录
- 用户的命令明确提到要创建新的 SDK 包
- 用户的命令明确提到要修改 `scripts/`、`.claude/` 等框架目录

### 不确定时的处理

如果 AI 无法判断当前应该处于哪种模式：
1. 必须先询问用户
2. 不得擅自进入 SDK 开发模式
3. 不得擅自修改框架层文件

## 项目创建流程

当用户说"创建一个新项目"或"开始一个新工作"时：

1. **创建项目目录**：
   ```bash
   mkdir -p D:\infra_demo\<project-name>
   ```

2. **切换到项目目录**：
   ```bash
   cd D:\infra_demo\<project-name>
   ```

3. **在项目目录中开发**：
   - 调用 SDK 工具
   - 编写项目代码
   - 不修改框架层文件

4. **项目命名规则**：
   - 使用 kebab-case（如 `my-web-app`）
   - 不得与框架目录冲突（不能命名为 `sdks`、`scripts`、`docs`、`.claude` 等）

---

## HARD GATES（强制规则）

### MUST（必须遵守）

1. **默认项目开发模式**：
   - 除非明确触发 SDK 开发模式，否则始终处于项目开发模式
   - 在项目开发模式下，不得修改框架层文件

2. **项目隔离原则**：
   - 用户项目必须在 `D:\infra_demo\` 下的独立子目录中
   - 项目目录不得与框架目录冲突

3. **新功能优先在项目中实现**：
   - 当需要新功能时，先在项目目录中实现
   - 等功能验证成熟、稳定后，再询问用户是否迁移到 SDK

4. **模式切换确认**：
   - 如果不确定当前应该处于哪种模式，必须先询问用户
   - 如果需要修改 SDK，必须先确认用户意图

### FORBIDDEN（禁止行为）

1. **禁止在项目开发模式下修改框架层**：
   - 不允许修改 `sdks/` 目录下的任何文件
   - 不允许修改 `scripts/` 中的框架工具
   - 不允许修改 `.claude/` 中的配置和 skills
   - 不允许修改 `docs/` 中的规范文档

2. **禁止假设用户意图**：
   - 不允许在没有明确触发条件的情况下进入 SDK 开发模式
   - 不允许擅自将项目代码迁移到 SDK

3. **禁止在根目录直接创建项目文件**：
   - 项目文件必须在项目子目录中
   - 不允许在 `D:\infra_demo\` 根目录直接创建 `index.js`、`main.py` 等项目文件

## 示例场景

### 场景 1：创建 Web 应用（项目开发模式）

**用户命令**：
```
"帮我创建一个 Web 应用"
```

**AI 行为**：
1. 询问项目名称（如 `my-web-app`）
2. 创建项目目录：`mkdir -p D:\infra_demo\my-web-app`
3. 切换到项目目录：`cd D:\infra_demo\my-web-app`
4. 在项目目录中搭建 Web 应用
5. 调用 SDK 工具（如果需要）
6. 不修改框架层文件

### 场景 2：添加 SDK 工具（SDK 开发模式）

**用户命令**：
```
"修改 infra-core SDK，添加新的审计功能"
```

**AI 行为**：
1. 识别到明确的 SDK 修改命令
2. 进入 SDK 开发模式
3. 修改 `sdks/infra-core/api/audit.py`
4. 更新相关的 tests 和文档
5. 运行 `audit-sdk` 验证

### 场景 3：功能成熟后迁移（询问用户）

**场景**：
用户在项目中实现了一个通用的数据验证功能，已经验证成熟。

**AI 行为**：
1. 识别到这个功能具有通用性
2. 询问用户："这个数据验证功能看起来很通用，是否考虑将它迁移到 SDK 中，以便在其他项目中复用？"
3. 等待用户确认
4. 如果用户同意，进入 SDK 开发模式，将功能迁移到 SDK

## 实施计划

### 第一步：更新 CLAUDE.md

在 `CLAUDE.md` 的"关键规则（HARD RULES）"部分添加：

```markdown
### SDK 稳定性原则（CRITICAL）

**D:\infra_demo\ 是一个可移植的 IDE 平台，包含框架层和项目层。**

#### 架构定位

- **框架层**（稳定，不随意修改）：`sdks/`、`scripts/`、`.claude/`、`docs/`
- **项目层**（用户工作区）：在根目录下创建的项目子目录（如 `my-app/`）

#### 工作模式识别

AI 有两种工作模式：

1. **项目开发模式（默认）**：
   - 在 `D:\infra_demo\<project-name>\` 子目录中工作
   - 调用 SDK 的 API 和 CLI 工具
   - 不修改框架层文件

2. **SDK 开发模式**：
   - 只有在以下任一条件满足时才进入：
     - 当前工作目录是 `D:\infra_demo\` 且命令涉及修改框架层
     - 用户明确下达命令（包含"修改 SDK"、"扩展 SDK"、"创建 SDK 工具"等关键词）
     - 用户的命令意图明确表示要修改框架层文件

#### HARD GATES（必须遵守）

**MUST**：
- 默认项目开发模式，除非明确触发 SDK 开发模式
- 用户项目必须在独立子目录中，不得与框架目录冲突
- 新功能优先在项目中实现，成熟后再询问是否迁移到 SDK
- 不确定模式时，必须先询问用户

**FORBIDDEN**：
- 禁止在项目开发模式下修改 `sdks/`、`scripts/`、`.claude/`、`docs/`
- 禁止在没有明确触发条件的情况下进入 SDK 开发模式
- 禁止在根目录直接创建项目文件（必须在项目子目录中）
```

### 第二步：更新工作流程

在 `CLAUDE.md` 的"工作流程"部分更新：

```markdown
## 工作流程

当收到新需求时，按以下顺序执行：

### 1. 判断工作模式

- 默认：项目开发模式
- 检查是否满足 SDK 开发模式的触发条件
- 不确定时询问用户

### 2. 项目开发模式流程

```
1. 确认项目目录 → 是否已有项目目录？
   ↓ 没有
2. 创建项目目录 → mkdir D:\infra_demo\<project-name>
   ↓
3. 切换到项目目录 → cd D:\infra_demo\<project-name>
   ↓
4. 查看现有 SDK → python scripts/list_tools.py
   ↓
5. 有现成能力？ → 调用 SDK API 或 CLI
   ↓ 没有
6. 在项目中实现功能
   ↓
7. 功能成熟后，询问是否迁移到 SDK
```

### 3. SDK 开发模式流程

```
1. 确认用户意图 → 确实要修改 SDK？
   ↓ 是
2. 查看现有 SDK → ls sdks/
   ↓
3. 按规范创建/扩展 SDK：
   - [ ] sdks/<sdk>/api/<module>.py
   - [ ] sdks/<sdk>/tests/test_<module>.py
   - [ ] sdks/<sdk>/skills/<skill>.md
   - [ ] .claude/skills/<sdk>-<skill>.md
   - [ ] 更新 manifest.yaml
   ↓
4. 运行 audit-sdk 验证
   ↓
5. 完成
```
```

### 第三步：更新 AI 行为约束

在 `CLAUDE.md` 的"AI 行为约束"部分添加：

```markdown
### 创建项目前

- 询问项目名称和用途
- 在 `D:\infra_demo\` 下创建项目子目录
- 不要在根目录直接创建项目文件

### 创建项目时

- 先切换到项目目录

### 创建项目后

- 不要擅自修改框架层文件
```

## 预期效果

实施此设计后，预期达到以下效果：

1. **清晰的职责分离**：
   - 框架层：稳定的工具库
   - 项目层：灵活的用户工作区

2. **更好的可维护性**：
   - SDK 不会被项目特定需求污染
   - 框架保持可移植性

3. **更安全的 AI 行为**：
   - AI 默认不会修改框架层
   - 只有在明确条件下才修改 SDK

4. **更好的用户体验**：
   - 用户可以在统一的工作空间中管理多个项目
   - 所有项目共享同一套 SDK 工具
